# 챗봇 답변 시간 줄이기

## 1. 시간을 어디에 쓰는가 (질문 1개)

기존 방식(`baseline`)은 질문마다 아래를 **차례로** 한다.

| 단계 | 호출 | 비고 |
| --- | --- | --- |
| 검색어 추출 | LLM 1회 | 프롬프트 1 |
| 항목 문서 수집 | 위키 1회 + 임베딩 | 처음 묻는 감염병일 때 |
| 검색어별 수집 (최대 3개) | 위키 검색 3회 + LLM 선별 3회 + 위키 본문 최대 6회 + 임베딩 | 처음 쓰는 검색어일 때 |
| 근거 검색 | 임베딩 1회 | |
| 답변 생성 | LLM 1회 | 답이 다 만들어진 뒤에야 화면에 나옴 |
| (화면) 대화 요약 | LLM 1회 | 답변 뒤에 |

처음 묻는 감염병이면 LLM 최대 6회가 줄지어 일어나고, 화면에는 마지막에 한꺼번에 나온다.

## 2. 줄이는 방법 (모두 `config/rag_settings.json`에서 켜고 끔)

| 방법 | 설정 | 무엇이 줄어드나 |
| --- | --- | --- |
| 수집 병렬화 | `parallel_collect: true` | 항목 문서를 검색어 추출과 동시에, 검색어별 검색·선별·본문을 동시에 → 수집 단계가 가장 느린 검색어 하나만큼 |
| 답변 스트리밍 | `stream_answer: true` | 총 시간은 같지만 **첫 글자**가 바로 나와 체감 대기 시간이 크게 줄어듦 |
| 필요할 때만 수집 | `collect_policy: when_needed` | 이미 모은 문서가 있으면 검색어 추출·수집 생략 → LLM 1회(답변)만 |
| 배경 수집 (권장) | `collect_policy: background` | when_needed처럼 바로 답하고, 이번 질문에 맞는 문서 수집은 뒤에서 → 다음 질문의 근거가 풍부해짐 |
| 같은 질문 저장 | `answer_cache: true` | 같은 감염병·같은 질문은 저장된 답(7일)으로 즉시 |
| 문서 미리 색인 | `python -m scripts.build_index --prefetch-docs` | 133개 감염병의 위키 문서를 미리 → **처음 묻는 질문도** LLM 1회 |
| 가벼운 보조 모델 | `aux_model: "gpt-4.1-nano"` 등 | 검색어 추출·후보 선별만 작은 모델로 (수집할 때만 영향) |
| 요약 LLM 끄기 | `summary_llm: false` | 오른쪽 요약을 답의 '핵심 답변'으로 → 질문당 LLM 1회 절약 |
| 답변 모델 변경 | `chat_model` | 모델마다 속도·품질이 다름 → `bench_chat --models`로 비교 |

## 3. 측정 결과

### 3-1. 모의 측정 (이 저장소의 작업 환경, 네트워크 없음)

GMS·위키백과에 접속할 수 없는 환경이라, 가짜 LLM·위키·임베딩에 흔한 지연(보조 LLM 1.0초, 답변 3.0초 중 첫 글자 0.7초,
위키 검색 0.5초, 본문 0.6초, 임베딩 0.3초)을 넣어 **흐름의 차이**만 쟀다. 숫자는 모의값이며, 호출 수는 실제 코드 그대로다.
가짜 위키에는 '홍역' 문서뿐이라 cold 수집량이 실제보다 적다(실제 cold는 LLM·위키 호출이 더 많아 차이가 더 커진다).

`python -m scripts.bench_chat --fake --ui`

| 설정 | cold 총 | cold 첫 글자 | warm 총 | warm 첫 글자 | 평균 | LLM 호출 cold/warm | 기존 대비 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| baseline | 6.87s | 6.87s | 4.32s | 4.32s | 5.60s | 3 / 2 | - |
| parallel | 5.97s | 5.97s | 4.32s | 4.32s | 5.14s | 3 / 2 | 8% 단축 |
| stream | 5.97s | 3.83s | 4.33s | 2.18s | 5.15s | 3 / 2 | 8% (첫 글자 44~50% 단축) |
| when_needed | 5.97s | 3.83s | 3.32s | 1.17s | 4.64s | 3 / 1 | 17% 단축 |
| background | 5.97s | 3.83s | 3.32s | 1.18s | 4.64s | 3 / 1 | 17% 단축 |
| cache (같은 질문 반복) | | | | | 0.00s | 0 | 즉시 |
| **prefetch** | 3.34s | 1.17s | 3.32s | 1.18s | **3.33s** | 1 / 1 | **41% 단축** |

- 첫 글자까지 기다리는 시간: 6.87s(기존 cold) → **1.17s**(prefetch), 4.32s(기존 warm) → **1.18s**.
- Streamlit 화면 자체가 더하는 시간: 질문당 **0.08초**(LLM 요약을 끈 뒤). 처음 측정 때 1.08초였는데, 원인은 화면이 아니라
  오른쪽 요약의 LLM 호출이었다 → `summary_llm: false`로 해결.
- 따라서 **Streamlit을 다른 수단(FastAPI+JS 등)으로 바꿔도 줄어드는 시간은 0.1초 미만**이다. 시간은 거의 전부 LLM·위키 호출에서 나온다.

### 3-2. 최종 실측 (2026-10-22 16:09, `bench_chat --quick`, SSAFY GMS·위키백과, gpt-4.1-mini)

| 설정 | cold 총 | cold 첫 글자 | warm 총 | warm 첫 글자 | 평균 | LLM 호출 cold/warm | 위키 호출 cold | 기존 대비 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| baseline (기존) | 18.09s | 18.09s | 18.86s | 18.86s | 18.48s | 5 / 5 | 7 | - |
| background (기본값) | 8.49s | 6.97s | 2.44s | 1.42s | 5.46s | 1 / 1 | 2 | **70% 단축** |
| **prefetch** (+ 문서 미리 색인) | 6.95s | 3.27s | 2.18s | **1.10s** | **4.57s** | 1 / 1 | 0 | **75% 단축** |

단계별 평균 (초): 검색어 · 수집 · 근거 검색 · 답변

| 설정 | cold | warm |
| --- | --- | --- |
| baseline | 1.1 · **12.8** · 0.3 · 3.8 | 2.6 · **12.4** · 0.3 · 3.6 |
| background | 0.0 · 3.3 · **2.7** · 2.4 | 0.0 · 0.0 · 0.3 · 2.1 |
| prefetch | 0.0 · 0.0 · **2.4** · 4.5 | 0.0 · 0.0 · 0.2 · 1.9 |

성과
- **질문당 평균 18.48초 → 4.57초 (75% 단축)**, 첫 글자까지 18초대 → warm 1.1초 / cold 3.3초.
- LLM 호출 질문당 5회 → 1회 (같은 질문 반복은 0회, 저장된 답).
- 기존 시간의 70%가 '수집'(12.8초)이었고, 이를 질문 경로에서 빼서 얻은 효과가 가장 크다.
- 남은 병목: 작업 공간마다 **첫 근거 검색이 2.4~2.7초**(이후 0.2~0.3초) → 임베딩 연결을 처음 여는 비용.
  앱 시작 때 임베딩을 배경에서 한 번 호출해 연결을 미리 열도록 했다(`warmup`, `service/runtime.py`).
  이 측정 뒤에 넣은 변경이라 표에는 아직 반영되지 않았다.
- 측정 중 'prefetch' 단계 직전에 보인 `배경 수집 실패 … FileNotFoundError`는 측정 스크립트가 배경 수집이 끝나기 전에
  임시 폴더를 지워서 생긴 것으로, 앱 동작과는 무관하다(스크립트 수정 완료).

### 3-3. 첫 실측 (2026-10-22 15:2x, 전체 설정, 한도 초과로 중단)

`python -m scripts.bench_chat` 결과. when_needed 세 번째 감염병에서 **GMS 사용 한도 초과(429 `organization_spend_limit_exceeded`)**로
중단되어 background·cache·prefetch는 측정하지 못했다.

| 설정 | cold 평균 | cold 첫 글자 | warm 평균 | warm 첫 글자 | 평균 | LLM 호출 cold/warm | 기존 대비 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| baseline | 38.73s | 38.73s | 33.06s | 33.06s | 35.90s | 5 / 4.7 | - |
| parallel | 27.14s | 27.14s | 21.65s | 21.65s | 24.39s | 5 / 4.7 | 32% 단축 |
| stream | 26.44s | 25.04s | 29.59s* | 28.27s | 28.01s | 5 / 4.7 | 22% 단축 |
| when_needed (2종) | 38.78s | 31.22s | **2.36s** | **1.44s** | 20.57s | 5 / **1** | 43% 단축 (warm 93% 단축) |

\* 뎅기열 warm 한 건이 44.9초로 튐 (GMS 응답 시간 변동). 감염병별 원자료는 측정 출력 그대로 보관.

읽는 법
- **수집을 건너뛴 warm 질문은 2.4초**(LLM 1회, 첫 글자 1.4초)인데, 수집하는 질문은 20~50초다.
  답변 생성 자체는 2초 안팎이고, 나머지는 **질문 도중의 수집**(보조 LLM 4회 + 위키 검색·본문 + 임베딩)이다.
- 병렬화로 수집 시간이 약 30% 줄었지만, 수집을 질문 경로에서 **빼는 것**이 가장 효과가 크다.
- 스트리밍은 첫 글자를 앞당기지만, 수집이 길면 첫 글자도 수집이 끝나야 나와서 효과가 작다. 수집을 뺀 뒤에야 1초대가 된다.

이 결과로 `background`의 cold(처음 묻는 감염병) 처리를 바꿨다: 검색어 추출·선별(LLM)이 필요한 수집은 답한 뒤 배경에서 하고,
**LLM이 필요 없는 항목 자체 위키 문서 1건만 바로 색인**해서 답한다(답변 LLM 1회). 이 경로의 실제 시간은 한도가 열린 뒤
`python -m scripts.bench_chat --quick`(baseline·background·prefetch만, 사용량 절약)으로 측정한다.

### 3-4. 측정 방법

```bash
python -m scripts.bench_chat --quick                                 # baseline·background·prefetch만 (권장, 사용량 절약)
python -m scripts.bench_chat                                         # 설정 7가지 모두
python -m scripts.bench_chat --models gpt-4.1-mini,gpt-4.1-nano,gpt-4o-mini   # 답변 모델 비교 (background 설정)
python -m scripts.bench_chat --configs baseline,background --aux-model gpt-4.1-nano   # 보조 모델
```

결과는 `reports/bench_chat.md`(표 + 단계별 평균)와 `reports/bench_chat.json`(질문별 상세, 질문마다 저장)에 남는다.
사용 한도 초과(429)로 멈추면 그때까지의 결과로 보고서를 만든다. 측정은 지금 색인을 임시 폴더에 복사해서 하므로
실제 `data/chroma`·캐시는 바뀌지 않는다. **측정 1회(7가지 설정)에 LLM 호출이 약 100회** 들어가므로 GMS 한도에 주의.

## 4. 선택한 기본값과 이유 (실측 반영)

| 설정 | 값 | 이유 |
| --- | --- | --- |
| `collect_policy` | `background` | 최종 실측 평균 18.48초 → 5.46초. 처음 묻는 감염병도 항목 문서 1건만 바로 색인하고 답함 |
| `parallel_collect` | `true` | 배경·첫 수집 시간 32% 단축(실측), 결과는 순차와 같음(테스트) |
| `stream_answer` | `true` | 수집을 뺀 질문에서 첫 글자 1.4초(실측) |
| `answer_cache` | `true` | 같은 질문 즉시, LLM 호출 0 → 한도 절약에도 도움 |
| `summary_llm` | `false` | 질문당 LLM 1회 절약 |
| `aux_model` | `""` | 한도 초과로 비교 못 함. 한도가 열리면 `--aux-model`로 비교 후 결정 |
| 문서 미리 색인 | **권장 (최종 선택)** | `build_index --prefetch-docs` 한 번이면 평균 4.57초, 첫 글자 cold 3.3초·warm 1.1초 |
| `warmup` | `true` | 앱 시작 때 임베딩 연결을 미리 열어 첫 근거 검색 2.4초를 없앰 |

참고: background는 수집을 **뒤로 미룰 뿐** 수집 LLM 호출 수는 같다. GMS 한도가 빠듯하면 `max_queries`를 3 → 1~2로 줄이면
배경 수집의 LLM 호출이 함께 줄어든다.

화면에는 답마다 `⏱ 2.4초 · 첫 글자 1.4초 · LLM 1회 (근거 검색 0.3 · 답변 2.0)`처럼 실제 걸린 시간이 표시된다.
